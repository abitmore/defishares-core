DefiShares Gold Feed Policy
===========================

Overview
--------

This document describes the DefiShares smartcoin feed changes introduced on branch `defishares`
in commit `09492788` (`Add DefiShares gold-based feed policy`).

The goal of this change set is to replace direct `TARGET/BTS` witness feeds with a GOLD-centered
feed model:

1. `GOLD/BTS` is calculated automatically by the chain.
2. Other BTS-backed smartcoins publish `TARGET/GOLD`, then the chain derives `TARGET/BTS`.

This document is intended for developers who need to understand the implementation details,
extension points, and current boundaries of the feature.

Scope of the Current Implementation
-----------------------------------

Implemented in this change:

- automatic `GOLD/BTS` feed generation;
- scheduled refresh of GOLD-derived feeds;
- `TARGET/GOLD` feed acceptance for BTS-backed bitassets;
- derivation of `TARGET/BTS` from `TARGET/GOLD * GOLD/BTS`;
- unit tests for the new feed behavior.

Not implemented in this change:

- removal of margin call logic;
- removal of settlement or liquidation logic;
- migration of non-BTS-backed smartcoins to this policy.

Important: existing call order and settlement paths are still active. This change only modifies
how feed prices are supplied and derived.

Protocol-Level Behavior Changes
-------------------------------

Compared with upstream BitShares behavior, the DefiShares branch changes smartcoin feed semantics
at the protocol behavior level in the following ways:

1. GOLD becomes the protocol anchor for BTS-backed smartcoins

   Upstream BitShares expects witnesses to publish direct `TARGET/BTS` settlement feeds for
   BTS-backed bitassets. DefiShares changes that expectation by introducing `GOLD` as the common
   anchor asset for feed routing.

2. GOLD feed is no longer witness-authored

   In upstream behavior, settlement pricing originates from witness-published feed data. In
   DefiShares, `GOLD/BTS` is generated by chain logic from a deterministic formula, so witnesses
   do not control the effective GOLD settlement price.

3. Witness feed direction changes for non-GOLD BTS-backed bitassets

   After `GOLD` exists, witnesses are expected to publish `TARGET/GOLD` instead of `TARGET/BTS`
   for BTS-backed bitassets other than GOLD itself.

4. Direct `TARGET/BTS` publication becomes invalid once GOLD is available

   This is an intentional protocol behavior change. The evaluator rejects direct core-backed feed
   publication for non-GOLD BTS-backed smartcoins after GOLD is present, forcing all such assets
   onto the GOLD-centered path.

5. Effective chain feed is now derived, not directly published

   For non-GOLD BTS-backed smartcoins, the witness-provided median feed is treated as source input
   (`TARGET/GOLD`), while the chain-derived `current_feed` becomes the effective `TARGET/BTS`
   value consumed by the rest of the engine.

6. Feed refresh timing changes from purely publication-driven to scheduled recalculation

   GOLD repricing is refreshed automatically on a 9600-block cadence, and dependent smartcoin
   `current_feed` values are recalculated from preserved witness median data whenever the schedule
   triggers.

7. `core_exchange_rate` is no longer required as the primary witness-provided control point

   Validation was relaxed so the protocol no longer assumes witnesses must provide a complete
   directly-usable core-based feed package in the old format for DefiShares feed flow.

Compatibility Notes
-------------------

- Existing witnesses and tools written for direct `TARGET/BTS` publication will need adjustment
  for DefiShares BTS-backed smartcoins.
- Feed publishers must treat `GOLD` as a required prerequisite asset for the new routing model.
- Downstream indexers, UIs, or ops tooling that read only `median_feed` should understand that
  the stored witness median may now intentionally differ from the effective `current_feed`.
- Margin call, force settlement, and liquidation logic remain active, so this branch is not a
  full protocol simplification yet; it is specifically a feed-path adjustment.

Feed Model
----------

### 1. GOLD feed is system-generated

The chain treats a market-issued asset whose symbol is exactly `GOLD` as the anchor asset.

`GOLD` does not depend on witness-published settlement prices. Its settlement price is calculated
internally as:

`GOLD/BTS = V0 * 10^(2 * sqrt(years_since_creation))`

where:

- `V0` is anchored as `1 GOLD / 1 BTS` in current implementation;
- `years_since_creation` is derived from elapsed blocks;
- elapsed time is quantized to 9600-block intervals.

Implementation details:

- update interval: `9600` blocks;
- blocks per year constant: `28800 * 365`;
- price direction is always kept in native BitShares settlement direction: `debt / collateral`.

For GOLD this means:

- `base = GOLD`
- `quote = BTS`

That choice avoids the common inverse-price mistake. The internal formula is written directly in
the same direction used by `settlement_price`.

### 2. Other BTS-backed bitassets publish TARGET/GOLD

Once a valid `GOLD` bitasset exists, non-GOLD bitassets backed by core asset `BTS` are expected
to publish witness feeds in this direction:

`TARGET/GOLD`

Example:

- `USDBIT/GOLD`
- `CNYBIT/GOLD`

These feeds are stored as the median witness feed input. The chain then derives:

`TARGET/BTS = TARGET/GOLD * GOLD/BTS`

The derived `TARGET/BTS` is written to `current_feed`.

### 3. Direct TARGET/BTS publishing is rejected after GOLD exists

After `GOLD` exists, a non-GOLD BTS-backed bitasset may no longer publish a direct `TARGET/BTS`
feed. This is enforced during feed evaluation.

This keeps all BTS-backed smartcoins on a single GOLD-based reference path.

Implementation Details
----------------------

### GOLD asset detection

The helper namespace `graphene::chain::defishares` identifies the anchor asset by:

- exact symbol match: `GOLD`
- asset must be market-issued

See:

- `defishares::gold_symbol()`
- `defishares::is_gold_asset()`
- `defishares::find_gold_asset()`

### Automatic GOLD initialization

When the `GOLD` bitasset is created, `asset_create_evaluator::do_apply()` immediately calls
`update_bitasset_current_feed()` so the asset starts life with a valid automatic feed.

Without this step, a newly-created GOLD asset would exist before its first scheduled refresh but
would not yet have the expected automatic current feed.

### Scheduled refresh

The scheduled recalculation happens from `database::update_global_dynamic_data()` on every block.

`defishares::refresh_scheduled_feeds()`:

- finds the GOLD asset;
- checks whether the current head block is aligned to a 9600-block boundary relative to
  `gold.creation_block_num`;
- if aligned, updates all bitasset current feeds;
- if a current feed changed, calls `check_call_orders()` using the refreshed feed.

This means GOLD-driven repricing is block-driven, not maintenance-interval-driven.

### Feed derivation behavior

`apply_feed_policy()` is called from `database::update_bitasset_current_feed()`.

Behavior:

1. If asset is `GOLD`
   - recompute automatic `GOLD/BTS`;
   - write it to both `median_feed` and `current_feed`;
   - mirror it into `core_exchange_rate`.

2. If asset is not `GOLD`
   - keep witness median feed intact;
   - if median feed is `TARGET/GOLD` and backing asset is BTS, derive `TARGET/BTS`;
   - write only the derived value into `current_feed`.

This distinction matters:

- `median_feed` preserves the witness-supplied `TARGET/GOLD` source data;
- `current_feed` exposes the chain-derived `TARGET/BTS` price used by the rest of the engine.

This was an important correction during development. If `median_feed` is overwritten with the
derived `TARGET/BTS`, later GOLD price movement can no longer re-derive from the original
`TARGET/GOLD` input.

### MCR, MSSR, ICR behavior

The change does not remove risk parameters.

The following values still come from the existing bitasset feed/options flow:

- `maintenance_collateral_ratio`
- `maximum_short_squeeze_ratio`
- `initial_collateral_ratio`

For GOLD, option extension overrides are still applied on top of the automatically generated feed.

Validation Rules
----------------

`asset_publish_feed` validation was relaxed so `core_exchange_rate` is no longer required at the
protocol validation layer. The test helpers and feed update path can still populate it, but the
DefiShares logic now recomputes the effective value where needed.

During evaluation:

- direct backing-asset feed is still accepted in the traditional case;
- after GOLD exists, non-GOLD BTS-backed assets must publish `TARGET/GOLD`;
- GOLD itself continues to use automatic chain-generated pricing.

Testing
-------

The following unit tests were added in `tests/tests/bitasset_tests.cpp`:

- `defishares_gold_feed_is_automatic`
- `defishares_target_gold_feed_is_derived_to_core`
- `defishares_gold_manual_feed_does_not_override_automatic`
- `defishares_target_gold_feed_uses_median_before_derivation`
- `defishares_rejects_direct_core_feed_once_gold_exists`

These tests verify:

- GOLD initializes automatically;
- GOLD reprices on the expected scheduled boundary;
- `TARGET/GOLD` is converted into `TARGET/BTS`;
- witness median is taken before derivation;
- manual direct `TARGET/BTS` publication is rejected once GOLD exists.

The test command used during implementation:

    cd build/tests
    ./chain_test --run_test="bitasset_tests/defishares_*" --log_level=test_suite

Current Boundaries and Developer Notes
--------------------------------------

1. This design currently targets BTS-backed market-issued assets only.

2. The symbol `GOLD` is a hard-coded anchor. If future work wants multiple anchors or a different
   symbol policy, the current implementation will need refactoring.

3. The initial anchor value is currently fixed at `1 GOLD / 1 BTS`. If the business rule changes,
   update:

   - `DEFISHARES_INITIAL_GOLD_PER_BTS_NUMERATOR`
   - `DEFISHARES_INITIAL_GOLD_PER_BTS_DENOMINATOR`

4. Scheduled updates use block height alignment, not wall-clock timestamps.

5. Existing liquidation and settlement logic remains live. Any future work that removes those paths
   will require additional changes outside the feed subsystem.
